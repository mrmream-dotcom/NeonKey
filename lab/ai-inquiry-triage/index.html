What it does

One message goes in. One structured result comes out:

  • Category: new project or sale, support problem, billing, partnership, spam, or other.
  • Urgency: low, medium or high, with a one-line reason.
  • Summary: one or two sentences, so you get the gist without rereading.
  • Key details: name, business, what they need, deadline, budget and contact info, but only when the message actually says them. Blank means it wasn't mentioned.
  • Suggested next step and a drafted reply you can edit. Anything the AI can't know, like a price or a date, is left as a [placeholder] for you to fill in.

Why a small business would want it

  • Sorting: sales leads, support problems and billing questions land in the same inbox. A label on each one lets you deal with them in batches, or route them to the right person.
  • Faster first replies: starting from a draft is quicker than starting from a blank email.
  • Fewer missed messages: an urgent "our booking form is broken" gets flagged instead of sitting under ten newsletters. Spam gets labelled so you can skip it.

It won't run your inbox for you. It does a first pass so you can spend your time on the reply.

How it works

  1. Form: this page sends the message (max 2,000 characters) to a small API.
  2. Worker: a Cloudflare Worker checks where the request came from (only neonkey.tech is allowed), applies the rate limits, and rejects anything empty or too long.
  3. AI: the Worker sends the message to Google's Gemini model with instructions and a strict JSON schema. The schema fixes the allowed categories and urgency levels, so the answer always has the same shape. The message is treated as data, so instructions hidden inside it are ignored.
  4. Structured result: the Worker checks the JSON and returns it. Nothing is saved.
  5. Human review: you read the summary and the draft, fix anything that's off, and send it yourself. In a real setup the result would go to a shared inbox label, a spreadsheet row or a task, not straight back to the customer.

Stack & tools

  • Astro (static page)
  • Cloudflare Workers (free plan)
  • Durable Objects (rate-limit counters only)
  • Google Gemini API (free tier)
  • JSON-schema structured output

What it costs to run

For this demo, nothing so far. Each piece runs on a free tier, and each has limits:

  • Cloudflare Workers, free plan: 100,000 requests a day and 10 ms of CPU time per request. The rate-limit counters live in a small Durable Object; the free plan includes 100,000 Durable Object requests and 100,000 written rows a day, and each run here uses only a handful of each. The 150-runs-a-day cap mainly protects the AI quota.
  • Google Gemini API, free tier: Google sets per-model request limits on the free tier and changes them from time to time. The trade-off is data use. On the free tier Google may use what's submitted to improve its products, and human reviewers may read it. Google's terms also don't allow free-tier apps for users in the UK, Switzerland or the EEA, so the demo is switched off there.
  • Size of a run: the example runs below used about 580–831 tokens each (instructions + message + result), as reported by the API.

For a real business handling customer messages, I'd use Gemini's paid tier, or another provider with similar terms. On the paid tier Google says it doesn't use prompts or responses to improve its products. It bills per token at Google's current rates (opens in new tab). For short messages like these the bill is usually small, but it depends on your volume, so I'd check it with you during scoping. I won't promise you a number here.

Limitations

  • The AI can misclassify. A vague message, sarcasm or a mix of topics can get the wrong label or urgency. Treat the result as a suggestion.
  • A human should review every reply. The draft can sound confident and still be wrong, and it doesn't know your prices, calendar or policies.
  • It only sees the one message. It has no customer history, so it can't tell an important repeat client from a stranger.
  • Free tiers can run out or slow down. If the main model is busy, the Worker retries on a lighter model. If both are unavailable, you get a friendly error instead of a result.
  • Rate limits are per connection, not per person. People behind the same office network, mobile carrier or VPN share one limit, and someone switching IP addresses can get around it. The daily total cap is the backstop.

Build notes: what broke and what I changed

  • The planned model wasn't available. I planned to use Gemini 2.5 Flash, but the API key returned "no longer available to new users." I switched to gemini-3.5-flash (the API currently reports the version it serves as gemini-3.6-flash) with thinking set to its minimal level (about 2–3 seconds per run), with Gemini 3.5 Flash-Lite as the fallback.
  • The newest model was too slow for a demo. The latest Flash model either returned "high demand" errors or took close to a minute during testing. For this job, speed matters more than having the newest model.
  • Free tier rules shaped the design. Google's terms say free-tier content may be reviewed and free-tier apps can't be offered in the UK, Switzerland or the EEA. That's why the page has a clear "don't paste private info" note and the Worker turns those regions away. A client build would use a paid tier.
  • The first rate limiter didn't hold. I started with Cloudflare's built-in rate limiting plus KV counters. In testing, a burst of requests sailed past the 5-a-minute limit: both are eventually consistent, so counts lag behind fast requests. I moved the counters into a small Durable Object, which handles one request at a time per visitor, and the limit then held in testing.
  • Fallbacks happen. One of the example runs below (the "something is broken" sample) was answered by the Flash-Lite fallback, because the main model didn't return a usable answer at that moment. The page shows which model answered every run.
  • Limits before AI. The Worker checks origin, rate limits and message length before it calls the AI, so abuse costs as little as possible.

The Worker source lives in the site's repository under workers/triage/, with no secrets in it. The API key is stored as an encrypted Worker secret.
